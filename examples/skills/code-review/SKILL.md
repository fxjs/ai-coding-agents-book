# 代码审查

目标：找出**会导致线上问题**的问题，而不是风格偏好。宁可少报，不可误报。

## 步骤

1. 确定范围（按优先级取第一个可用的）：
   - 用户在参数里给了范围：`$ARGUMENTS`
   - `git diff --staged` 有内容 → 审查暂存区
   - 否则 `git diff` 工作区
   - 都没有 → 审查 `HEAD~1..HEAD`
2. 先读 `AGENTS.md`（或 `CLAUDE.md`）里团队约定，把它们当作规则的一部分。
3. 逐文件读 diff，同时读**改动点上下文**（不是只看 diff 行）。
4. 对每个可疑点，尝试构造一个能失败的输入；构造不出来就不要报。
5. 输出报告，不要顺手改代码（除非用户明确要求修复）。

## 检查清单

按此顺序检查，前面的问题优先级更高：

| 级别 | 类别 | 具体看什么 |
|---|---|---|
| P0 | 正确性 | 边界条件、空值、off-by-one、并发竞态、错误吞掉 |
| P0 | 安全 | 注入、路径穿越、密钥泄漏、越权、依赖投毒 |
| P1 | 数据 | 迁移不可逆、写放大、缺事务、时区/编码 |
| P1 | 兼容性 | 公共 API/CLI 参数/配置字段的破坏性变更 |
| P2 | 可观测性 | 失败无日志、日志含敏感信息、错误码混乱 |
| P3 | 可维护性 | 重复逻辑、命名误导、缺测试覆盖关键分支 |

## 输出格式

```text
## 结论
<一句话：可以合并 / 修完 P0 再合并 / 需要重新设计>

## 问题
### P0 · <文件>:<行> · <标题>
- 现象：<什么情况下会出问题>
- 证据：<相关代码片段，≤6 行>
- 建议：<最小修复，不重写>

## 测试缺口
- <哪个行为没有测试覆盖>

## 我确认过没问题的点
- <列出你重点看过但判断没问题的部分，减少读者重复劳动>
```

## 硬性约束

- 每条问题必须能指出具体文件与行号。
- 不确定的写成「待确认」，不要断言。
- 不评论纯格式（缩进、引号、行宽），除非团队 linter 未覆盖且会引发 bug。
- 报告用中文，代码标识符保留原文。
